## 1. Threat model

**What is protected, in order:** the homelab behind the VPS; player accounts and data (Discord ids, Minecraft links, session addresses); the world and its backups (NFS share, S3); what friends install (the exe, its self-update, the pack); secrets (`deploy/.env`, WireGuard keys, the deploy key, SSH keys, Discord bot and OAuth secrets, GitHub and GHCR tokens, Actions secrets).

**Who would realistically attack a friends' server, and how:**

| Attacker | What they can reach | What they want | Where it is stopped today |
|---|---|---|---|
| Internet scanner | Caddy on 443, UDP 51820, the home's 25565 (mc-router), Discord's side of the bot | A foothold, a crash, disk or CPU | TLS and a login on every page; WireGuard drops unauthenticated packets; mc-router drops unknown hostnames; Mojang auth on the game |
| A leaked invite link or launcher token | One member's view: mod list, downloads, votes, wake, install reports; an admin's token can also Start the server | To play, to spam, to impersonate | Invite: used once, 7 days. Token: 7 days, revoked on removal, on leaving Discord, on uninstall |
| A friend's PC with malware | That friend's launcher token, their Minecraft session, their browser cookies | Same as above, plus the game account | The token is good for the member's own rights only; nothing on the PC reaches the VPS or the homelab beyond the public routes |
| A friend's Discord account taken over | Sign-in as that friend (Discord OAuth); vote, wake and chat into the game through the bot; an admin's account: restart, say, feed | The site as that member; for an admin, the admin pages and the Minecraft console | Admin password sign-in is separate and needs a TOTP; the console is Minecraft only and audited |
| A bad mod or a bad dependency | Code on every PC (client mods), in the instance container on the AMP host (server mods), in `web` or `api` (npm) | Everything | Lock pins exact Modrinth versions with checksums; CI builds from the lockfile; Snyk watches `main` |
| A mistake in the public repo | Secrets or private data in a commit | Keys, addresses, names | `.env` and keys are git-ignored; pre-push greps; the history was rewritten once (2026-10-05) |
| A break-in to `web` (a Next.js bug) | The internet-facing container: `api` with the service token as any role, the database, `modpack/` and `.git` read-write, `data/` | The homelab through `api`, root on the VPS through the deploy, every PC through the mod list and the exe | `api` only does named, validated, audited operations; the deploy key is rrsync-only; the web container has a memory cap and runs unprivileged. What remains is tracked privately |
| Alex's GitHub account taken over | CI, GHCR, Actions secrets, `main` | A signed-looking exe and images on every PC and the VPS | 2FA on the account (GitHub requires it for contributors); branch protection on `main` |

Not in the model: a nation state, a targeted attack on Alex personally, physical access to the homelab.

## 4. TLS and certificates: the decision

Weighed against the table above, for Alex to accept or reject.

| Option | What it protects against | What it costs to build and run | What breaks for a friend when it goes wrong | Recommendation |
|---|---|---|---|---|
| **Leave public CA TLS through Caddy** for browsers and the app (the state today), HSTS on | Reading or changing traffic on the path; a fake site, as long as the trust store is sound | Nothing: Caddy renews itself | Nothing new | **Keep** |
| **Certificate or public key pinning in the app** | A rogue CA, or a compromised trust store on the PC (malware that installs its own root) | Let's Encrypt renews the leaf every 60 to 90 days, so a leaf pin breaks every PC within three months. An intermediate or root pin (ISRG Root X1/X2) lasts years but Let's Encrypt may change issuers without notice, and a pin set with a backup pin must be shipped before it is needed. A pinned app can only be fixed by an update, which arrives over the pinned channel: once a pin is wrong, every friend downloads the exe again by hand | The app refuses to talk to the site, with no way to fix it but a fresh download and a SmartScreen warning | **Reject.** The threat it covers (a CA or trust-store attack on a friend's PC) is not in the model, and the failure mode strands every friend at once |
| **Client certificates (mutual TLS) for the app** | An attacker with a stolen token but no certificate | Caddy client-auth config plus a certificate issued per PC through the device flow, stored next to the token it would protect. Revocation lists or short lifetimes to manage. Everything a stolen token can do today, a stolen certificate and key file can do too, because both sit in the same folder on the PC | Expired or lost certificate = cannot play until re-approved; the same step as today's token, with more that can go wrong | **Reject.** The device-flow token already is a per-PC credential with the same lifetime and revocation; a certificate adds no protection against the realistic case (malware on the PC) |
| **Mutual TLS between `web` and `api`**, a CA in a container that is not always on | Someone on the `internal` Docker network who is not root | The client key would live in the `web` container next to `API_SERVICE_TOKEN`; a break-in takes both. A stopped CA container's key is still on the VPS disk, readable by root. Long-lived certificates renewed by hand, which means an expiry date that takes the site down | The site stops working on the day a certificate expires, until someone notices | **Reject.** Only root sees that network, and root already has `.env`. A CA is only offline on another machine |
| **TLS on the internal hops** (`web` → `api`, `api` → AMP) | As above | `api` → AMP is already inside WireGuard (keyed both ends, encrypted). `web` → `api` never leaves the host | n/a | **Reject** for both. Already covered |
| **Code signing the exe and signing what the site hands out** (the self-update offer, later the mod list) | **A compromised VPS or `web` serving a bad exe to every PC on the next Play.** This is the one attack in the model that TLS of any kind cannot stop, because the attacker *is* the server with the valid certificate. Also a compromised GHCR package | A signing key the VPS never holds; the public key built into the exe; a signature file next to the exe in CI; a check before every self-update. Rotation: two public keys in the exe (current and next); a lost key means one fresh download by hand per PC. Where the key lives is the real decision: a GitHub Actions secret signs on every `main` build and moves the risk to Alex's GitHub account; a key on Alex's PC is stronger and makes every app release a manual step | A wrong signature = the update is refused and the app carries on as it is (today's behaviour on a wrong checksum). Nothing is stranded unless the key is lost, which costs one download per PC | **Accept, in two steps.** Step 1 now: sign the exe in CI with an Actions secret, verify in the app before a self-update; check the Java and NeoForge downloads against published checksums at the same time. Step 2 later, if wanted: a signed mod list, which moves Lock off the VPS and is Alex's workflow call. Authenticode through Azure Artifact Signing is a separate, optional purchase for the SmartScreen box (docs/07 "Signing") and does not replace step 1 |

**The recommendation in one line:** keep public TLS as it is, pin nothing, add no client certificates or internal TLS, and spend the effort on signing the exe (and checking Java and NeoForge downloads) so that a compromised VPS cannot push code to every friend's PC. Alex accepted the recommended option on 2026-10-07 (the build order, private).

## 7. How this register is used

- Open findings, specs and the build order: the private repository, branch `security`. The building sessions report there and in docs/11.
- A report is reviewed with Approved, Approved with follow-ups or Blocked. "Done" without the command output or the diff stays Open.
- When a finding is Fixed or Verified it is written here with its evidence, and the private copy is trimmed.
